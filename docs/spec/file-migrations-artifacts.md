# File Migrations Artifact Specification

## Status

Draft

## Purpose

Define the on-disk artifacts for Grizzle's file-based migration workflow.

Pinned upstream target:

- Drizzle ORM / Drizzle Kit `v1.0.0-rc.1`

## Scope

This document must define:

- migration directory layout
- migration filenames
- numbering rules
- snapshot format
- SQL segmentation format
- edited migration expectations

This document also locks the supported artifact scope for the initial implementation.

- Drizzle Kit generate docs

## Directory Layout

Upstream Drizzle guidance establishes these artifact concepts:

- migrations output directory (`out`, default `./drizzle`)
- migration subdirectories
- `migration.sql` inside each migration subdirectory
- `snapshot.json` inside each migration subdirectory

Grizzle adopts the same artifact shape with Grizzle-branded defaults and stricter validation.

## Supported Artifact Scope

Initial Grizzle support is intentionally narrow:

- supported: Drizzle RC.1-style folder-per-migration artifacts
- unsupported: old journal-based migration folders
- unsupported: mixed-format migration directories
- unsupported: ad hoc flat directories of standalone `.sql` files with no approved artifact structure
- unsupported: any target artifact model that depends on `meta/`

If the input migrations directory does not match the supported artifact format, Grizzle must fail with a clear error instead of trying to upgrade or infer intent.

## Supported Artifact Format

The supported artifact format for the initial Grizzle design is:

```text
<migrations-out>/
  <YYYYMMDDHHmmss>_<suffix>/
    migration.sql
    snapshot.json
  <YYYYMMDDHHmmss>_<suffix>/
    migration.sql
    snapshot.json
```

Notes:

- each migration is represented by a dedicated directory
- migration identity is the directory name
- `migration.sql` is the executable SQL payload
- `snapshot.json` captures schema state for diff/generation workflows

This structure is based on the Drizzle RC.1-era folder-per-migration model and is the only format Grizzle supports initially.

Default output directory for Grizzle:

```text
./grizzle
```

Normative rules:

- the configured migrations output directory is the root artifact directory
- each migration artifact is represented by one immediate child directory of that root
- each valid migration directory must contain these required files:
  - `migration.sql`
  - `snapshot.json`
- no `meta/` directory is part of the supported artifact contract
- the migration directory name is the canonical migration identity

Extra files in migration directories are invalid for the initial strict artifact model. This is DEVIATION:INTENTIONAL artifact-shape hardening relative to RC.1, whose runtime ignores extra files.

Intentional stricter divergence:

- Drizzle RC.1 runtime discovers migrations by `migration.sql` and does not require runtime `snapshot.json`
- Grizzle requires `snapshot.json` for every supported migration artifact so `check`, `generate`, and `migrate` operate on one coherent artifact graph
- this is **DEVIATION:INTENTIONAL** runtime-strictness hardening: Grizzle must not apply SQL-only migration folders that cannot participate in future snapshot-graph validation or generation

## Artifact Kinds

The initial design supports three artifact kinds:

- generated migration
- custom migration
- introspection migration generated by `pull`

All artifact kinds use the same directory shape:

- `migration.sql`
- `snapshot.json`

No sidecar kind file and no `meta/` directory are introduced.

Kind-specific SQL content:

- generated migrations do not require a kind marker/header
- custom migrations generated by `generate --custom` use the Drizzle RC.1-style placeholder comment:
  - `-- Custom SQL migration file, put your code below! --`
- introspection migrations generated by `pull` use a managed header inside inert SQL:
  - `-- grizzle:managed-introspection v1`
- the managed header is DEVIATION:INTENTIONAL bootstrap-safety metadata and does not introduce a sidecar kind file
- an artifact is managed-introspection when the first non-empty physical line of `migration.sql`, after an optional UTF-8 BOM, is exactly `-- grizzle:managed-introspection v1`
- normal `migrate` must reject pending or unrecorded managed-introspection artifacts with `bootstrap_init_required`; once `pull --init` records one by `name`, later `migrate` runs skip it like any other applied migration
- conversion to a normal custom migration requires removing the managed header and intentionally making the SQL executable; comment-only SQL with schema-changing snapshot state remains invalid outside `pull --init`

Content rules:

- placeholder comments are part of the hashed file bytes
- managed introspection headers are part of the hashed file bytes
- placeholder comments do not replace snapshot validation or graph validation
- custom migrations do not bypass graph, history, or hash validation

## Migration Filename Format

For the RC.1 target model, migration identity is the migration directory name, not just the SQL filename.

Supported format:

```text
<YYYYMMDDHHmmss>_<suffix>
```

Where:

- `YYYYMMDDHHmmss` is a 14-character UTC timestamp prefix
- `_` separates timestamp from the human-readable migration suffix
- `<suffix>` is the generated or developer-provided name component

`migration.sql` always lives inside that directory.

Normative rules:

- the timestamp prefix must be exactly 14 decimal digits
- the timestamp prefix must encode UTC calendar components in `YYYYMMDDHHmmss` order
- the separator between timestamp and suffix must be a single underscore
- the suffix must be non-empty
- the full directory name must be used as the migration `name` recorded in history

Initial character policy for `<suffix>`:

- lowercase ASCII letters, decimal digits, underscores, and hyphens are allowed
- spaces are not allowed
- path separators are not allowed
- the full migration directory name must be no more than 255 bytes when encoded as UTF-8
- because the initial suffix character set is ASCII, this is also a 255-character maximum for supported names
- Grizzle must preserve valid user-provided names within this allowed set
- Grizzle must normalize generated default suffixes into this form
- when no suffix is supplied, the production generator must copy Drizzle RC.1's default `adjective_hero` suffix shape using RC.1-derived adjective and hero word lists
- generated names remain second-precision in the timestamp prefix, matching RC.1 upstream behavior

Suffix strictness note:

- RC.1 uses the provided `--name` suffix directly when constructing the folder name
- Grizzle validates explicit suffixes before creating directories so user input cannot create confusing paths, whitespace-sensitive identities, or platform-specific invalid names
- this is DEVIATION:INTENTIONAL path-safety hardening

Timestamp note:

- Grizzle uses UTC calendar components for all timestamp prefix fields
- RC.1 generation source mixes local year with UTC month/day/time, while RC.1 runtime parses with `Date.UTC(...)`; Grizzle treats that as an upstream edge mismatch and normalizes to all-UTC generation and parsing
- this is DEVIATION:INTENTIONAL timestamp-determinism hardening

Examples of valid names:

- `20260504130510_init`
- `20260504130645_add_users_table`
- `20260504130702_seed_users`
- `20260504130715_seed-users`

Examples of invalid names:

- `20260504130510`
- `20260504130510_add users`
- `init`

User-provided name handling:

- if a user provides a migration name that already conforms to the allowed suffix character set, Grizzle must preserve it
- if a user provides a migration name that does not conform to the allowed suffix character set, the command must fail with `invalid_migration_name`
- if the full generated migration directory name would exceed 255 bytes, the command must fail with `invalid_migration_name`
- the initial spec does not require silent normalization of arbitrary user input
- automatic normalization is reserved for generated default suffixes, not for invalid explicit names

## Ordering Rules

RC.1 ordering behavior derived from tagged runtime:

- artifact discovery sorts migration directories lexicographically by directory name
- runtime extracts the first 14 characters of the directory name
- those 14 characters are interpreted as UTC timestamp components
- migration identity for pending detection is still the full directory name, not timestamp alone

Implication for Grizzle:

- ordering and identity are related but not identical
- timestamp prefix determines chronological ordering
- full directory name determines migration identity

Normative ordering rules:

- artifact discovery must sort candidate migration directories lexicographically by full directory name
- the timestamp prefix is the primary chronological ordering key
- the full directory name is the identity key used by history and pending detection
- Grizzle must not collapse distinct migration directories merely because they share the same timestamp prefix

If two migration directories share the same 14-character timestamp prefix:

- they remain distinct migrations if their full names differ
- lexicographic directory ordering still determines their relative execution order
- later specs may define whether Grizzle generates such names itself, but the artifact format must tolerate them as distinct identities

Generation-time duplicate-name rule:

- if `generate` computes a migration directory name that already exists, the command must fail with `duplicate_migration`
- the initial spec does not require automatic retry, renaming, or higher-than-second timestamp precision
- this matches the RC.1 shape more closely than inventing a stronger collision-avoidance mechanism at spec time

## Artifact Discovery Rules

Artifact discovery is RC.1-derived, with the intentional strict divergences below.

Valid migration artifacts are only:

- immediate subdirectories of the configured migrations output directory
- where each such subdirectory contains `migration.sql`
- and the subdirectory name matches the supported migration identity format

Invalid artifact inputs include:

- flat `.sql` files in the root output directory
- journal-based folder layouts
- missing `migration.sql`
- partial or mixed migration directories

Grizzle must fail early on invalid artifact layouts rather than inferring intent.

Normative discovery and validation rules:

- every immediate child directory of the configured output directory must be either a valid migration artifact or an explicitly ignored reserved temporary directory
- discovery must enforce the active resource limits for artifact count, directory-entry count, total artifact bytes, `migration.sql` bytes, `snapshot.json` bytes, snapshot JSON depth/entity count, and reserved temporary cleanup scan count
- limit checks must be applied while walking/loading, before buffering whole files or parsing JSON where size metadata is available, and must honor context cancellation
- resource-limit failures return the stable `resource_limit` error code and must not be reported as malformed snapshots or unsupported artifact formats
- root-level `.sql` files must not be treated as migrations
- a candidate directory is valid only if:
  - its directory name matches the supported migration identity format
  - `migration.sql` exists as a regular file within that directory
  - `snapshot.json` exists as a regular file within that directory
- if any non-reserved child directory is malformed or has an invalid migration name, the command must fail with `unsupported_artifact_format` or the more specific stable code before silently skipping it
- if the output directory contains legacy-format markers such as `meta/_journal.json`, the command must fail with an unsupported-format error
- if a migration directory contains files other than `migration.sql` and `snapshot.json`, the command must fail with an unsupported-format error
- root-level `.sql` files fail with `unsupported_artifact_format`
- root-level `migrations.js`, `migrations.ts`, `migrations.mjs`, and `migrations.cjs` bundle files fail with `unsupported_artifact_format`; Expo/Durable SQLite bundle generation is unsupported in the initial Grizzle target
- root-level editor/metadata files such as `.gitkeep`, `.DS_Store`, and `README`/`README.md` are the only ignored sidecars in the initial target
- unknown root-level regular files fail with `unsupported_artifact_format` unless a future explicit allowlist is specified; they must not be silently ignored or treated as secret-inspected migration inputs
- root-level non-regular files other than valid migration directories and reserved temporary directories fail with `invalid_path`

The initial design is strict. Discovery is not a best-effort scan.

Extra-file strictness note:

- RC.1 runtime ignores extra files inside migration directories and can create root-level bundle files such as `migrations.js`
- RC.1 bundle files are unsupported in the initial Grizzle target; if present, root-level `migrations.js`, `migrations.ts`, `migrations.mjs`, and `migrations.cjs` fail with `unsupported_artifact_format`
- Grizzle rejects extra files inside migration directories so each applied artifact is exactly the graph unit validated by `check`
- this is DEVIATION:INTENTIONAL artifact-shape hardening
- only explicitly allowed editor/metadata files are ignored at the root; all other root-level sidecars fail as unsupported according to the discovery rules above and must not influence discovery, ordering, hashing, or execution

### Path Containment

Artifact loading must not follow paths outside the configured migrations output directory.

Normative rules:

- resolve `migrations-out` to a canonical real path before discovery
- artifact-consuming commands must `Lstat` the configured root and reject a symlinked migration root unless a future explicit opt-in is designed
- only immediate child directories under that real path may be migration candidates
- migration directories must be real directories, not symlinks
- `migration.sql` and `snapshot.json` must be regular files, not symlinks
- any resolved artifact path outside `migrations-out` must fail with `invalid_path`
- root-level `.sql` files, nested migration directories, path traversal, and non-regular artifact files are invalid
- hard links must be rejected where the platform exposes enough metadata to detect unsafe aliasing

### Output Write Safety

The same containment posture applies when `generate` or `pull` writes artifacts.

Normative rules:

- if the output root exists, resolve it to a canonical real path before writing and reject a symlinked root unless a future explicit opt-in is designed
- if the output root does not exist, resolve and canonicalize its parent directory, create the root with no-follow directory creation semantics where the platform supports them, then canonicalize the created root before writing artifacts
- write only within the configured output root
- create migration directories as new real directories, not symlinks
- fail if the target migration directory already exists
- fail if target files already exist as symlinks, hard links, non-regular files, or paths outside the output root
- write artifact contents in a hidden child directory of the output root and sibling of the final migration directory, named `.grizzle-tmp-<uuid>`
- `.grizzle-tmp-<uuid>` names are not migration candidates because valid migration identities must start with a 14-digit timestamp prefix
- stale `.grizzle-tmp-<uuid>` directories are ignored by `check`/`migrate` discovery but may be cleaned by `generate`/`pull` before writing new artifacts
- stale temporary cleanup must operate only under the canonical output root, must use `Lstat`/no-follow traversal, must delete only real directories whose basename exactly matches `.grizzle-tmp-<uuid>`, must never follow symlinks, and must fail or ignore safely when a matching path is not a real directory
- any other child directory under the root, including other dot-directories, must fail discovery with `unsupported_artifact_format`
- completed artifacts must be published with atomic rename where the platform supports it
- if same-filesystem atomic publication is unavailable, Grizzle must fail closed unless a future spec defines a fallback that preserves no-discoverable-partial, no-follow creation, final revalidation, fsync, and digest verification invariants
- staging must never occur inside the final timestamped migration directory; the final directory appears only after all required files are complete
- failed writes must not leave a directory that passes artifact discovery
- staging must stay on the same trusted filesystem as the final output root; cross-device publication is disallowed unless a future spec defines safe copy, revalidation, fsync, and digest verification semantics
- staging directories must be created with private permissions such as `0700` where the platform supports them and with no-follow directory creation semantics
- after publish, the implementation must re-read or otherwise verify final `migration.sql` and `snapshot.json` bytes/digests before returning the created artifact
- do not follow symlinks when creating or replacing `migration.sql` or `snapshot.json`; managed source files use the same safety posture through `ManagedSourceStore`

## Snapshot Format

Each migration directory must contain a `snapshot.json` file.

Role of `snapshot.json`:

- it is generation metadata, not executable SQL
- it captures the schema snapshot associated with that migration artifact
- it participates in migration-graph ancestry and branch analysis
- it is a required input to `check`

Normative snapshot rules for the initial implementation:

- `snapshot.json` is required for every migration directory, including custom migrations
- `snapshot.json` must be valid JSON
- `snapshot.json` must match the supported Grizzle snapshot schema for the selected dialect
- commands that depend on snapshot analysis must fail on malformed or unsupported snapshot versions

Grizzle takes the core snapshot envelope directly from Drizzle RC.1 source.

Initial top-level snapshot contract:

```json
{
  "version": "<dialect-version>",
  "dialect": "<dialect-id>",
  "id": "<uuid>",
  "prevIds": ["<uuid>", "..."],
  "ddl": [],
  "renames": []
}
```

Normative top-level fields:

- `version`
  - dialect-specific snapshot version string copied from the RC.1 validator family
- `dialect`
  - dialect discriminator copied from the RC.1 validator family
- `id`
  - snapshot identity as a UUID string
- `prevIds`
  - zero-or-more parent snapshot IDs expressed as UUID strings
- `ddl`
  - dialect-specific ordered DDL entity array using the RC.1 `createDDL()` entity definitions for the selected dialect
- `renames`
  - ordered rename metadata array preserved from Drizzle RC.1 snapshots as an array of strings

Rename metadata encoding:

- Grizzle must write `renames` using Drizzle RC.1's `prepareMigrationRenames` format.
- Each rename string is `from->to`.
- Each side is assembled as optional `schema + "."`, optional `table + "."`, and required `name`, omitting absent schema/table segments exactly as RC.1 does.
- Rename strings are derived from validated, typed `RenameDecision` / `EntityRef` values; the public resolver must not supply raw rename strings.
- The string array is compatibility metadata in `snapshot.json`; diff generation must use the typed decisions before serialization rather than reparsing ambiguous strings as the authoritative rename model.

RC.1-aligned dialect/version map:

- PostgreSQL: `version = "8"`, `dialect = "postgres"`
- MySQL: `version = "6"`, `dialect = "mysql"`
- SQLite / libSQL / Turso: `version = "7"`, `dialect = "sqlite"`
- Cockroach: `version = "1"`, `dialect = "cockroach"`
- MSSQL: `version = "2"`, `dialect = "mssql"`
- SingleStore: `version = "2"`, `dialect = "singlestore"`

Initial Grizzle implementation scope:

- PostgreSQL, MySQL, and SQLite are the only required file-migration snapshot validators for the initial implementation
- Cockroach, MSSQL, SingleStore, libSQL/Turso-specific behavior, and other RC.1 dialect variants are future scope until corresponding Grizzle dialect/runtime support exists
- encountering an unsupported dialect snapshot must fail with `unsupported_dialect`

Initial ancestry rules copied from RC.1 behavior:

- snapshot ancestry is represented by `prevIds`
- linear history uses one parent ID
- merge history may use multiple parent IDs
- first generated migrations use the Drizzle sentinel origin UUID as their sole parent:
  - `00000000-0000-0000-0000-000000000000`

Root-normalization note:

- Drizzle RC.1 source is not perfectly uniform across dialects for `pull` bootstrap snapshots
- PostgreSQL-style paths use the sentinel origin UUID as a parent, while some other dialect paths use empty `prevIds`
- Grizzle intentionally normalizes supported initial root snapshots to `id = fresh UUID != origin UUID` and `prevIds = [origin UUID]` so `check`, `generate`, and graph validation have one root model
- artifact snapshots may reference the sentinel origin UUID only as a parent, never as their own `id`
- this is a DEVIATION:INTENTIONAL graph-normalization choice, not an accidental parity claim

DDL payload rule:

- `ddl` must use the dialect-specific entity format corresponding to the selected snapshot validator family
- Grizzle must treat the Drizzle RC.1 validator/source definitions as the authoritative schema for these entity records
- Grizzle does not need to invent a new top-level snapshot model

Normative DDL schema sources:

| Dialect | Snapshot source | DDL entity source |
| --- | --- | --- |
| PostgreSQL | `drizzle-kit/src/dialects/postgres/snapshot.ts` | `drizzle-kit/src/dialects/postgres/ddl.ts` |
| MySQL | `drizzle-kit/src/dialects/mysql/snapshot.ts` | `drizzle-kit/src/dialects/mysql/ddl.ts` |
| SQLite / libSQL / Turso | `drizzle-kit/src/dialects/sqlite/snapshot.ts` | `drizzle-kit/src/dialects/sqlite/ddl.ts` |
| Cockroach | `drizzle-kit/src/dialects/cockroach/snapshot.ts` | `drizzle-kit/src/dialects/cockroach/ddl.ts` |
| MSSQL | `drizzle-kit/src/dialects/mssql/snapshot.ts` | `drizzle-kit/src/dialects/mssql/ddl.ts` |
| SingleStore | `drizzle-kit/src/dialects/singlestore/snapshot.ts` | MySQL DDL wiring imported by `drizzle-kit/src/dialects/singlestore/snapshot.ts` |

The accepted initial field matrix is specified in [file-migrations-snapshot-fields.md](./file-migrations-snapshot-fields.md). Implementers must not treat the source paths above as the only discoverable contract.

Initial accepted object-family matrix:

| Dialect | `check` may accept and analyze initially | `generate` must produce initially | `pull` must emit initially |
| --- | --- | --- | --- |
| PostgreSQL | schemas, tables, enums, columns, indexes, foreign keys, primary keys, unique constraints, checks, and views | schemas, tables, enums, columns, indexes, foreign keys, primary keys, unique constraints, checks, and views | schemas, tables, enums, columns, indexes, foreign keys, primary keys, unique constraints, checks, and views |
| MySQL | tables, columns, primary keys, foreign keys, indexes, checks, and views | tables, columns, primary keys, foreign keys, indexes, checks, and views | tables, columns, primary keys, foreign keys, indexes, checks, and views |
| SQLite | linear graphs for tables, columns, indexes, foreign keys, primary keys, unique constraints, checks, and views; branched commutativity is unsupported initially | tables, columns, indexes, foreign keys, primary keys, unique constraints, checks, and views | tables, columns, indexes, foreign keys, primary keys, unique constraints, checks, and views |

Scope rules:

- `check` may accept only object families it can both validate and analyze for branch commutativity.
- `generate` may only emit object families that are representable by the selected `SchemaInput`.
- `pull` may only emit object families that can be faithfully represented in generated Go schema source.
- "columns" in the matrix means the supported column entity family and supported properties only; it does not imply every RC.1 column modifier is accepted.
- recognized but unsupported properties inside a supported object family, including generated columns, identity columns, dynamic runtime defaults, unsupported autoincrement modes, unsupported custom types, materialized views, unsupported view options, PostgreSQL `isRlsEnabled=true`, or unsupported dialect-specific index options, must fail with `unsupported_feature`.
- PostgreSQL standalone sequences, roles, privileges, and policies are recognized RC.1 object families but are unsupported in the initial accepted artifact graph unless and until corresponding validation, commutativity, and Grizzle schema APIs are explicitly designed; encountering any of these entity families fails with `unsupported_object_family`.
- if a selected schema input or live database contains an object family outside the initial `generate` or `pull` support column, the command must fail with `unsupported_object_family` rather than silently dropping it from `snapshot.json`.
- if a local `snapshot.json` contains a recognized RC.1 object family outside the initial `check` acceptance column, `check` must fail with `unsupported_object_family` rather than accepting an unanalyzable migration graph.
- Cockroach, MSSQL, and SingleStore snapshots are not required for the initial Grizzle implementation.
- SQLite branch graphs with multiple open leaves must fail with `unsupported_feature` until a SQLite commutativity engine is explicitly designed.

Initial field-level support rule:

- supported fields/properties must be listed in generated validator fixtures or a checked-in support matrix before implementation
- unsupported fields/properties in otherwise recognized RC.1 entities fail with `unsupported_feature`, not with a generic parse error
- unsupported whole entity families fail with `unsupported_object_family`
- unsupported static Go schema-loader constructs fail with `unsupported_schema_construct`

Implementation rule:

- the Go port must encode these RC.1 schemas as typed validators or generated schema fixtures, not as permissive untyped JSON maps
- snapshot validation must reject malformed JSON, wrong dialect, unsupported version, invalid UUIDs, invalid `prevIds`, invalid dialect DDL entities, and unknown top-level fields
- validation errors must include JSON-pointer-like paths such as `/ddl/3/table/name`
- compatibility tests must include representative RC.1 `snapshot.json` fixtures per supported dialect
- Grizzle intentionally uses stricter top-level validation than RC.1, whose simple validators are not strict about extra keys; this is DEVIATION:INTENTIONAL validation hardening

Reference publication requirement:

- the implementation must include generated or hand-maintained field-level references for the accepted RC.1 snapshot entities, starting with [file-migrations-snapshot-fields.md](./file-migrations-snapshot-fields.md)
- those references may be Go validator structs, JSON schema files, or checked-in fixture catalogs generated from the tagged RC.1 TypeScript source
- contributors must not need to re-read upstream TypeScript source to discover the field shape of every accepted DDL entity

Current evidence note:

- RC.1 docs clearly describe snapshot artifacts as part of generated migrations
- tagged runtime evidence confirms the folder-per-migration execution model
- `snapshot.json` in the migration directory is the target model for Grizzle's initial design

## SQL Segmentation Format

Upstream Drizzle runtime does not split on semicolons. It splits generated migration SQL on the explicit marker:

```text
--> statement-breakpoint
```

This upstream behavior is the default reference model for Grizzle.

Normative rules:

- `migration.sql` is stored as text
- `migration.sql` must be read, hashed, segmented, and validated using bounded readers capped by the active `MaxMigrationSQLBytes` and total-artifact limits
- `migration.sql` must be valid UTF-8; an optional leading UTF-8 BOM is allowed only for read-side compatibility and is ignored for managed-header detection but remains part of hashed raw bytes
- `migration.sql` must not contain NUL bytes or unsupported control characters other than tab, LF, and CR
- segmentation operates on the validated UTF-8 text after normalizing CRLF and CR to LF for delimiter-line detection only; execution preserves the original segment text bytes apart from removing delimiter lines
- statement boundaries for generated migrations are defined by the explicit `--> statement-breakpoint` marker, not by raw semicolon splitting
- execution logic must preserve this contract
- custom migrations that contain multiple statements must follow the same segmentation contract if they are intended to execute as multiple statements
- when no breakpoint marker is present, the file is one execution payload, matching Drizzle RC.1 runtime behavior
- the initial Grizzle workflow must not try to prove whether marker-free SQL contains one or many semicolon-separated statements; semicolon parsing remains non-target behavior
- generated multi-statement output must use breakpoints, and custom multi-statement SQL must include explicit breakpoint markers if it is intended to run as multiple executable payloads
- `generate` and `pull` must reject `breakpoints=false` until a future design adds explicit statement-count metadata or a proven SQL parser/executor strategy
- disabled or commented introspection SQL must not contain active delimiter lines whose trimmed content is exactly `--> statement-breakpoint`

This means semicolon-driven parsing is explicitly non-target behavior for file-based migrations.

## Edited Migration Policy

Migration artifacts are intended to be immutable once committed and applied.

Normative policy:

- editing an existing migration artifact after generation is discouraged
- editing a migration artifact after it has been applied to any shared environment is invalid workflow
- local `check` must compute stable artifact digests for reporting and deterministic diagnostics
- DB-backed execution follows Drizzle RC.1 pending detection by `name`; already-applied migrations are skipped without hash comparison

Digest policy:

- the DB history `hash` records the executable `migration.sql` hash for Drizzle RC.1 alignment
- local `check` must compute separate deterministic digests for `migration.sql` and `snapshot.json`
- local `check` must expose a combined artifact digest for diagnostics and TOCTOU prevention
- the combined artifact digest is not part of the initial history-table schema unless explicitly re-scoped later

Practical guidance:

- create a new migration instead of rewriting an established migration
- reserve custom migrations for intentional user-authored SQL, not for retroactive mutation of prior artifacts

## Custom Migrations

Custom migrations are in scope for the initial design.

Target behavior:

- Grizzle must support generating an empty migration artifact for user-authored SQL
- custom migrations must still use the canonical RC.1-style artifact layout
- custom migrations must still participate in `check`, `migrate`, and history tracking
- custom migrations must not bypass artifact validation, naming rules, or history semantics

Normative rules:

- a custom migration is still a normal migration artifact
- it must be assigned a normal migration directory name
- it must include both `migration.sql` and `snapshot.json`
- it must participate in the same ordering, branch, validation, and history rules as generated migrations
- its snapshot must have a fresh `id`
- its `prevIds` must come from `CheckResult.EffectiveParentIDs`, using the sentinel origin UUID for empty-graph first generation
- by default, its `ddl` must equal the effective parent DDL
- raw custom SQL is not parsed to infer snapshot changes
- initial custom migrations are intended for data changes or operational SQL that does not change schema shape tracked by snapshots
- schema-changing custom SQL is unchecked and unsupported in the initial workflow unless a future explicit custom-snapshot mechanism is added; the CLI and docs must warn that such SQL can make the live database diverge from `snapshot.json`
- this is DEVIATION:INTENTIONAL snapshot-coherence hardening relative to Drizzle's broader custom migration documentation

Custom migrations are not a side channel and do not define a separate artifact format.

The command behavior is defined in [file-migrations-generate.md](./file-migrations-generate.md).

## Unsupported Formats

The following are out of scope for the initial implementation:

- old Drizzle journal-based migration folders
- automatic conversion via a Grizzle equivalent of `drizzle-kit up`
- legacy Grizzle migration formats
- directory scans that treat any `*.sql` file as a valid migration artifact
- any artifact model that depends on a `meta/` directory

This is an intentional initial-scope exclusion. Grizzle is beginning with the RC.1-style artifact model and has no released old file-migration format that requires an upgrade path.

## Snapshot Schema Reference Publication

Initial scope decision:

- Grizzle implementation must include generated or hand-ported Go validators for the RC.1 dialect snapshot schemas
- representative RC.1-compatible JSON fixtures must be checked in for every supported dialect
- [file-migrations-snapshot-fields.md](./file-migrations-snapshot-fields.md) is the human-readable field reference for the initial accepted entity set
- the tagged Drizzle RC.1 source files remain canonical when the field reference and source disagree, but such disagreement must be fixed in the spec before implementation proceeds
- generated standalone reference schema files may be added for maintainability, but correctness is defined by validators plus fixtures derived from the RC.1 source
